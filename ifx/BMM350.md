# BMM350 magnetometer

## Board topology

The official CY8CKIT-062S2-AI schematic, **630-60699-01 revision 03,
sheet 10**, connects U19 BMM350 directly to `I2C_SCL_P0_2` and
`I2C_SDA_P0_3` (SCB0), not to U18 BMI270's auxiliary `ASCx`/`ASDx`
interface. ADSEL is high and the schematic explicitly specifies address
**0x15**. VDDIO uses 3.3 V; VDD uses 1.8 V. The CRST capacitor is 2.2 µF.
The same main bus contains BMI270 at 0x68 and DPS368 at 0x77.

Do not configure the existing BMI270 BMM150 auxiliary option for this board:
BMM150 and BMM350 have different IDs, registers, initialization and
compensation.

## Portable component

`sensor: {platform: bmm350}` uses ESPHome's ordinary I²C device interface;
it has no Zephyr or Infineon-specific sensor binding. The generic default
address is 0x14 (ADSEL low); only 0x14 and 0x15 are accepted. All four
outputs are optional:

```yaml
sensor:
  - platform: bmm350
    address: 0x15
    field_strength_x:
      name: Magnetic Field X
    field_strength_y:
      name: Magnetic Field Y
    field_strength_z:
      name: Magnetic Field Z
    temperature:
      name: Magnetometer Temperature
    update_interval: 1s
```

The limited initial implementation runs normal mode at 25 Hz with two-sample
averaging. `update_interval` controls publication, not the hardware ODR,
and must be at least 40 ms. Field outputs are in µT in the sensor's native
axes; temperature is the die temperature in °C. Board orientation, hard/soft
iron calibration, heading, interrupts, forced mode, self-test and runtime
configuration of ODR/averaging are outside this component's initial scope.

Initialization is asynchronous: 3 ms power-up allowance, soft reset and
24 ms wait, chip-ID 0x33 verification, all 32 OTP words with bounded
completion polling, OTP power-off, full bit reset (14 ms), flux-guide
reset (18 ms), measurement configuration and normal-mode transition (38 ms).
PMU command completion is checked before proceeding. Every register read
discards the two I²C dummy bytes. Data-ready is latched without enabling
the physical INT output; reads publish only a complete compensated sample.
Normal mode must report the selected effective ODR/averaging (status1 0x16)
before the component becomes ready.
OTP/I²C/PMU initialization errors fail the component visibly. Transient
measurement errors retain the last sample and set a warning that clears
on a successful read.

OTP decoding and offset, sensitivity, temperature and cross-axis
compensation follow the Bosch floating-point SensorAPI v1.10.0 equations.
The component does not include or upload firmware. Bosch's BSD-3-Clause
notice is retained in `esphome/components/bmm350/LICENSE.txt` and the
compensation header; redistribute that notice with binaries. The filename
matches the existing `MANIFEST.in` component-license rule; package-data
inclusion is enabled in `pyproject.toml`.

### Hardware setup correction and bounded PMU diagnostics

The first fresh kit capture reached `BMM350 smoke boot` and then failed at
`ODR status / normal mode`. That older combined error cannot distinguish
an I²C status-read failure, a PMU status mismatch, or a normal-command write
failure. It does not establish a root cause or successful sensor delivery.

The subsequent reviewed diagnostic established that startup command 0x02 was
rejected: status0 **0x10** means illegal=1, busy=0, normal=0 and completed
command=0. The snapshot read back aggregation **0x16**, command **0x02** and
effective configuration **0x14** (still the 100 Hz/two-sample setting),
not the requested 25 Hz/two-sample setting. This is a rejected command,
not a transport error or evidence requiring a longer wait.

Startup now writes aggregation, axes and interrupt settings in suspend after
magnetic reset, then issues **normal command 0x01 directly** and retains the
existing 38 ms transition wait. The unnecessary startup ODR-update command
0x02 and its 1 ms step are removed. The illegal flag is still fatal; status1
must confirm the effective requested configuration before readiness.

A failed PMU check
logs either an I²C error code or the actual status0 byte, expected/completed
command, busy, illegal-command, normal-mode and ODR/averaging override bits.
A status mismatch or failed PMU command write triggers **one read-only
five-register snapshot**, 0x04 through 0x08: aggregation, axes, command,
status0 and status1. A failed snapshot logs its own I²C error without retries.
Status checks and normal-command write failures have separate final reasons.
Normal-mode completion checks its command and power-mode bit in the same
status read.

Evidence from the official datasheet **BST-BMM350-DS002-29** and exact Bosch
v1.10.0 source pinned below:

- Datasheet page 14, §5.1.2: boot/initialization leaves the sensor in suspend.
  Page 16, **Figure 2**: magnetic reset returns unconditionally to suspend,
  and command **0x01** enters normal with averaging and ODR **as selected**.
  Page 33, §8.6: 0x01 is NM; 0x02 updates ODR/averaging, and normal mode
  accepts only SUS or UPD_OAE. Page 31, §8.4 encodes 25 Hz/two-sample as
  **0x16**; page 35, §8.8 defines status1's effective configuration.
- `bmm350.c:918–960` performs BR/FGR and checks completion. For a cold
  initialization, no normal mode is restored (lines 964–966).
  `set_powermode`, lines 2085–2106, writes the requested normal command
  and selects `BMM350_SUSPEND_TO_NORMAL_DELAY`, **38000 µs**.
- `bmm350.c:641–654` writes aggregation and command 0x02, then waits
  **1000 µs**, but checks only transport/delay success, not the illegal
  status flag. Calling that sequence in our suspended startup therefore
  did not prove command acceptance on the kit.
- `bmm350_defs.h:378–389` defines the status0 masks used by this driver;
  lines 536–544 encode completed commands. The bug was startup sequencing,
  not a wrong 0x02 encoding or a status mask that should be relaxed.
- `bmm350.c:551–590` reads the previous PMU command and, for normal or
  ODR-update commands, enters suspend before calling `set_powermode`.
  `bmm350_defs.h:224` specifies a **6000 µs** suspend wait. Our direct
  normal start follows magnetic reset's suspend state, not a previous
  normal/ODR-update request, so no additional suspend command/wait is needed.

The fake bus reproduces the kit's rejected ODR update in suspend rather than
echoing every command as successful. The normal-start regression checks
configuration latching and exact command order. Negative cases retain busy,
illegal (including observed 0x10 and apparently normal 0x38), missing normal,
wrong completion, status-read failure and stale/default effective settings.

## Verification and merge gate

The credential-free kit fixture is `ifx/fixtures/bmm350.yaml`. It deliberately
uses `scan: false`: zero-length address-only probes are rejected by the
pinned CAT1 HAL, so scanner absence is not evidence that a sensor is missing.
The driver's nonempty chip-ID/OTP/data transfers provide the actual check.
No Wi-Fi, API or OTA credentials are required.
UART0 (SCB5) is explicit. The fixture emits `BMM350 smoke boot` at boot
priority -100 and logs `BMM350 field_x=%.3f uT`, `field_y`, `field_z` and
`BMM350 temperature=%.3f C` directly from each sensor's `on_value` callback.
No timer reads cached `.state` to manufacture samples. Follow the
[fresh-capture bench protocol](HARDWARE_TESTING.md#bmm350-fresh-capture-smoke-test).

The corrected fixture passed on A1 silicon. The peer-reviewed HEX
`9705f9b2a269d235e31bf1d3b2b16888b372cf2bd627b4a7d2267abfc7ce0c16`
reported normal mode and published five fresh samples per channel:
X 22.086 to 22.208 µT, Y -6.005 to -5.590 µT, Z -3.297 to -2.453 µT,
and die temperature 37.712 to 37.829 °C. OpenOCD verified the 11,264-byte
tail scrub and the restored core image; three fresh core heartbeats followed.
This tests live reads, not calibrated accuracy.
[Bench evidence](https://github.com/ederjc/esphome/issues/6#issuecomment-7229970072).

Focused Python validation tests live in
`tests/unit_tests/components/test_bmm350.py`. C++ behavior tests live in
`tests/components/bmm350/test_bmm350.cpp` and use a dummy-byte-aware fake
I²C bus to cover initialization, first-error preservation, OTP timeout,
wrong device ID, PMU errors, signed data, compensation and transient recovery.

Run from the worktree with the existing fork Python environment:

```powershell
$env:PYTHONPATH = "$PWD"
..\esphome-psoc6\.venv\Scripts\python.exe -m pytest tests\unit_tests\components\test_bmm350.py -q --no-cov
..\esphome-psoc6\.venv\Scripts\python.exe script\cpp_unit_test.py bmm350
```

The runner selects filesystem test directories, not platform names:
`sensor.bmm350` would be filtered out as nonexistent. The BMM350
test manifest explicitly supplies the I²C and sensor dependencies instead.
Fork CI requires the BMM350 fixture to exist, compiles it unconditionally,
and executes this focused C++ selector on its Ubuntu runner. A Linux runner
failure is blocking; the Windows skip is never substituted for CI execution.

Author validation: 10 Python tests pass; Ruff lint/format, full language-schema
extraction (including all BMM350 fields), and ESP8266 portable source generation
pass. Full **CY8CKIT-062S2-AI native compilation and linking pass** with the
existing tagged Zephyr workspace, Arm SDK 1.0.1 and GCC 14.3. The fixture uses
the board's fixed SCB0 pins: this variant rejects explicit `sda`/`scl`.
The C++ behavior runner explicitly **skips Windows** with exit code 1, even
when `CC`/`CXX` point at the working GCC 14.3 cross-compiler. Its scheduler and

### Independent Bosch oracle

The exact v1.10.0 tag resolves to
`3daf377ccaf589319c0d41af192105e9275987a2`. Inspection disproves the proposed
Y/Z fixed corrections and sign-dependent temperature offset for this version:

- [`bmm350.c:1636`](https://github.com/boschsensortec/BMM350_SensorAPI/blob/3daf377ccaf589319c0d41af192105e9275987a2/bmm350.c#L1636):
  `sens_y = fix_sign(sens_y, BMM350_SIGNED_8_BIT) / 256.0f;` (no `+0.01f`).
- [`bmm350.c:1671`](https://github.com/boschsensortec/BMM350_SensorAPI/blob/3daf377ccaf589319c0d41af192105e9275987a2/bmm350.c#L1671):
  `tcs_z = fix_sign(tcs_z, BMM350_SIGNED_8_BIT) / 16384.0f;` (no `-0.0001f`).
- [`bmm350.c:1771`](https://github.com/boschsensortec/BMM350_SensorAPI/blob/3daf377ccaf589319c0d41af192105e9275987a2/bmm350.c#L1771):
  `out_data[3] = (float)(out_data[3] - (1 * 25.49));` unconditionally,
  including negative and zero raw temperature.

`tests/components/bmm350/vendor_oracle.py` downloads the three unchanged
vendor files at that immutable commit, verifies their SHA-256 digests, compiles
the real Bosch API and this component's real compensation header with
GCC 14.3/C++20, and executes them on the SDK's existing Cortex-M3 QEMU.
No PSoC 6 hardware or managed sources are changed. It exercises Bosch's actual
`bmm350_init`/OTP decoding and `bmm350_get_compensated_mag_xyz_temp_data`, not
another transcription of the equations. The `.cpp.template` stays outside
the upstream C++ test runner's source glob.

```powershell
..\esphome-psoc6\.venv\Scripts\python.exe tests\components\bmm350\vendor_oracle.py
```

**12 differential vectors pass**, with `rel_tol=2e-6`, `abs_tol=1e-5`.
They cover raw temperature +100000, -100000, 0, +1 and -1, signed XYZ,
all-zero OTP and nontrivial signed packed OTP (including temperature gain,
temperature sensitivity and cross-axis correction). Identical vendor output
vectors are retained in the C++ regression test. Representative nontrivial
OTP outputs from the unchanged vendor are:

| Raw temperature | X (µT) | Y (µT) | Z (µT) | Temperature (°C) |
| --- | --- | --- | --- | --- |
| +100000 | 713.20886230 | -878.45550537 | -1782.45812988 | 71.35444641 |

| 0 | 820.36145020 | -902.31976318 | -1944.04345703 | -26.39042854 |

These are synthetic differential inputs, not plausible-temperature limits or

`7e9794658daf6bdd4cb781e38bc1dd99d7d7f32a80fc221ee52e011b8f92fb2a`.
The oracle verifies compensation only, not ESPHome scheduler/I²C runtime behavior.

Use an isolated build/cache prefix when compiling the board fixture.
